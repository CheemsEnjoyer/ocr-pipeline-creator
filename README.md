# OCR Flow Studio

Интерактивный React-мастер, который создаёт OCR-пайплайн из четырёх последовательных вопросов: название, источник текста, способ OCR и правила извлечения данных.

## Страницы

- `/` — конструктор пайплайна. Готовый пайплайн сохраняется в `localStorage` браузера.
- `/process` — загрузка документов и запуск обработки. Файлы можно перетащить в область загрузки, выбрать один из сохранённых пайплайнов и обработать пакет: каждый файл уходит в `POST /api/pipeline/run` и получает свой статус и результат.
- `/history` — постоянная история успешно обработанных документов. Исходник можно просмотреть (PDF и изображения) или скачать, распознанный текст открыть отдельно, а извлечённые поля отредактировать и сохранить. Правки сохраняют типы JSON и не меняют исходный файл, распознанный текст и первоначальный ответ модели. При одновременном редактировании устаревшая версия не перезаписывает новые правки.

Разделы доступны в левом меню; на узком экране меню открывается кнопкой в заголовке.

## Локальный запуск

```bash
npm install
npm run dev
```

Приложение откроется на `http://localhost:5173`.

## Хранилище истории документов

История использует Cloudflare D1 (`DB`) для текста, полей и метаданных и R2 (`BUCKET`) для исходных файлов. Привязки заданы в `.openai/hosting.json`; на Sites они создаются платформой. История общая для пользователей, имеющих доступ к этому приложению. Пайплайны по-прежнему хранятся в браузере. Результаты обработок, выполненных до появления истории, автоматически восстановить нельзя.

Для первого локального запуска истории выполните сборку и примените миграцию к локальной базе:

```bash
npm run build
npx wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_third_power_pack.sql
npm run dev
```

Миграция применяется один раз к новой базе. При публикации Sites применяет миграции из `drizzle` автоматически. Файл ограничен размером 20 МБ. Документ появляется в истории после успешной обработки и сохранения исходника.

Проверка API на запущенном локальном сервере: `node scripts/test-document-history.mjs`. Она проверяет сохранение документа, чтение исходника, редактирование и повторное чтение полей, конфликт версий и валидацию; тестовый документ удаляется из локального хранилища.

## PostgreSQL

Схема находится в `database/schema.sql`. Она содержит типы документов, пайплайны, шаги, извлекаемые поля, файлы и историю запусков.

```bash
createdb ocr_flow
psql ocr_flow < database/schema.sql
```

Скопируйте `.env.example` в `.env` и задайте `DATABASE_URL`. В production рекомендуется держать загрузки в S3-совместимом object storage, а в PostgreSQL — метаданные, структуру пайплайна и результаты.

## Архитектура обработки

`POST /api/pipeline/run` принимает `multipart/form-data` с файлом и JSON-описанием пайплайна. Для цифровых документов текст читается напрямую, для сканов — через vision-модель LiteLLM (файл уходит как `data:`-URL) или через указанный OCR-сервис. Если извлечение включено, полученный текст отправляется в `POST /v1/chat/completions` с `response_format: json_object`.

Пайплайн хранит тип входных файлов, настройки OCR, режим извлечения, модель LiteLLM и `max_tokens`. Для сканов можно выбрать vision-модель LiteLLM, задать ей отдельный промпт либо указать URL OCR-сервиса. Если ответ Vision-модели уже является финальным результатом, шаг извлечения можно отключить. В остальных случаях извлечение настраивается целым промптом или набором именованных параметров. Список моделей загружается из `GET /v1/models`, выполнение идёт через `POST /v1/chat/completions`.

Для LLM настройте `LITELLM_BASE_URL` и `LITELLM_API_KEY` из `.env.example`. Ключ остаётся на сервере и не передаётся в браузер.
