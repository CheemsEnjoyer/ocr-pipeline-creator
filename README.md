# OCR Pipeline Creator

Конструктор OCR-пайплайнов и обработка документов. Интерфейс — React/Vinext, API — Python/FastAPI, база — PostgreSQL через SQLAlchemy, исходные файлы — S3. В левом меню доступны обработка, конструктор, пайплайны, история документов и API-ключи. Интерфейс закрыт логином и паролем администратора, внешние системы подключаются через отдельные API-ключи.

В разделе «Пайплайны» бокового меню отображаются сохранённые конфигурации. Нажмите на название, чтобы отредактировать настройки и сохранить тот же пайплайн, или на корзину, чтобы удалить его с подтверждением. Список обработки обновляется автоматически. Удаление пайплайна не удаляет документы из истории. Пайплайны хранятся в PostgreSQL.

## Запуск

Нужны Node.js 22.13+ и Python 3.10+ (при установке Python на Windows включите **Add Python to PATH**).
Перед запуском скопируйте `.env.example` в `.env` и настройте PostgreSQL и S3 по инструкции ниже.
Для локального запуска нужна доступная база PostgreSQL: задайте `DATABASE_URL`
или `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_DB` и `POSTGRES_PASSWORD`.

```powershell
npm install
npm run dev
```

При первом запуске автоматически создаётся `.venv` и устанавливаются Python-зависимости. Затем поднимаются Python API, Celery worker, диспетчер очереди и интерфейс. API применяет миграции Alembic перед запуском. Нужен доступный Redis (`CELERY_BROKER_URL`, по умолчанию `redis://127.0.0.1:6379/0`). Повторные запуски не переустанавливают зависимости, пока `backend/requirements.txt` не изменится. Активация виртуального окружения и ручные SQL-команды не нужны.

Откройте http://localhost:5173. Остановка всех процессов — `Ctrl+C`.

## Запуск через Docker

Нужен Docker Desktop с запущенным движком Linux containers и Docker Compose 2.24+.
Node.js и Python на компьютере для этого способа не нужны.

Скопируйте `.env.example` в `.env`, настройте подключение к существующей PostgreSQL
через `DATABASE_URL` или `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`,
`POSTGRES_DB`, `POSTGRES_PASSWORD`. Задайте `CELERY_BROKER_URL` существующего Redis и настройте S3;
при необходимости задайте пароль администратора и параметры LiteLLM.
Затем в папке проекта выполните:

```powershell
docker compose -f docker_compose.yaml up -d --build
```

Откройте http://localhost:5173. Логи: `docker compose -f docker_compose.yaml logs -f`.
Остановка: `docker compose -f docker_compose.yaml down`. После изменения кода повторите команду запуска со сборкой.

PostgreSQL и Redis должны быть запущены отдельно и доступны из контейнеров.
Compose не создаёт их контейнеры и тома. Сервис `migrate` применяет миграции к указанной базе;
приложение, воркер и диспетчер ждут его успешного завершения.
Celery worker и диспетчер запускаются автоматически. Воркер обрабатывает
до двух документов одновременно. Сохранение данных PostgreSQL и очереди Redis
настраивается на существующих серверах. Сгенерированный пароль администратора сохраняется в папке `data`
на компьютере. Уже существующая папка `data`
используется автоматически. Если пароль не задан, он находится в `data/admin-password.txt`.
Файл `.env` передаётся при запуске, данные и секреты в образ не копируются.
Новые исходные документы сохраняются в S3.

В контейнере интерфейс слушает `0.0.0.0:5173`, Python API — только `127.0.0.1:8000`.
Compose публикует интерфейс только на локальном компьютере. `PORT` в `.env`
меняет порт компьютера; внутренние порты, `HOST`, `BACKEND_URL` и `OCR_DATA_DIR`
зафиксированы в `docker_compose.yaml`. Для доступа с других компьютеров измените привязку
`127.0.0.1` в `ports` и настройте reverse proxy с HTTPS.

Если PostgreSQL, Redis, LiteLLM или OCR-сервис запущен на этом же компьютере, используйте в его адресе
`host.docker.internal` вместо `localhost` (Docker Desktop).

## PostgreSQL

Используется существующая база PostgreSQL. В `.env` задайте адрес сервера
`POSTGRES_HOST`, порт `POSTGRES_PORT`, имя базы `POSTGRES_DB`, пользователя
`POSTGRES_USER` и непустой `POSTGRES_PASSWORD`. Пользователь должен существовать.
Если базы нет, приложение перед миграциями подключается к служебной базе `postgres`
на том же сервере с теми же учётными данными и создаёт указанную базу.
Для этого нужны доступ к `postgres` и право `CREATEDB`. Если база уже доступна,
эти дополнительные права не требуются. Пользователю нужны права для применения миграций приложения.
Пароль передаётся драйверу отдельно, поэтому спецсимволы в `POSTGRES_PASSWORD`
не требуют URL-кодирования. Изменение этих переменных не меняет существующих
пользователей и их пароли в PostgreSQL.

Для отдельного сервера можно задать `DATABASE_URL`, например:

```dotenv
DATABASE_URL=postgresql+psycopg://ocr:password@db.example.com:5432/ocr
```

`DATABASE_URL` имеет приоритет над `POSTGRES_*`. Адреса с `postgresql://`
и `postgres://` также используют драйвер Psycopg 3. Для URL спецсимволы в логине
и пароле должны быть URL-кодированы. Соединения проверяются перед повторным использованием.
Описание драйвера: [SQLAlchemy PostgreSQL/Psycopg](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#module-sqlalchemy.dialects.postgresql.psycopg).

SQLite больше не используется приложением. Существующий `data/ocr.sqlite3`
не удаляется и автоматически не переносится; для сохранения старой истории нужен
отдельный перенос записей в PostgreSQL. По умолчанию API-тесты используют временную SQLite-базу.
Чтобы прогнать тот же набор на PostgreSQL, задайте `TEST_DATABASE_URL` перед
`npm run test:backend`. Тесты создают и удаляют собственные схемы; тестовому
пользователю нужны права на создание схем в указанной базе.

## S3: исходные файлы

Все новые исходные файлы сохраняются в существующий приватный S3-бакет.
Без `S3_BUCKET_NAME` (или `S3_BUCKET`) API не запускается; при ошибке S3 файл не сохраняется локально,
а запрос возвращает HTTP 503. Бакет автоматически не создаётся.

Пример `.env`:

```dotenv
S3_BUCKET_NAME=ocr-documents
S3_REGION=us-east-1
S3_ACCESS_KEY_ID=your-access-key
S3_SECRET_ACCESS_KEY=your-secret-key
S3_PREFIX=originals
```

Для S3-совместимого сервиса задайте `S3_ENDPOINT_URL`, например
`http://host.docker.internal:9000` для MinIO на компьютере с Docker Desktop,
и при необходимости `S3_ADDRESSING_STYLE=path`.
Поддерживаются и прежние имена `S3_BUCKET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.
При наличии новых переменных `S3_BUCKET_NAME` и пары `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`
они имеют приоритет; оба ключа пары должны быть заданы вместе.
Для AWS оставьте `S3_ENDPOINT_URL` пустым. Вместо явных ключей можно использовать
стандартную цепочку учётных данных Boto3, включая IAM role; временные ключи требуют
`AWS_SESSION_TOKEN`. Старые переменные `OBJECT_STORAGE_*` не используются.

Приложению нужны права `s3:PutObject`, `s3:GetObject` и `s3:DeleteObject`
на объекты выбранного префикса. Удаление используется для очистки после неудачной
записи в базу. Публичный доступ и CORS бакету для интерфейса не нужны:
исходник выдаёт API после проверки сессии администратора. Для просмотра API создаёт
временную копию файла и удаляет её после ответа, включая ответы на Range-запросы.

Ключ объекта хранится в PostgreSQL; смена `S3_PREFIX` влияет только на новые файлы.
Смену бакета или endpoint выполняйте вместе с переносом объектов: старые ключи
читаются из текущего бакета. Старые исходники в `data/originals` остаются доступными
и автоматически в S3 не переносятся. После изменения `.env` в Docker выполните
`docker compose -f docker_compose.yaml up -d --force-recreate`.

SDK S3: [официальная документация Boto3](https://docs.aws.amazon.com/boto3/latest/reference/services/s3.html).

## Celery: фоновая обработка

Режимы задаются для каждого пайплайна: можно разрешить синхронный запуск, асинхронный
запуск или оба варианта. Если разрешены оба, режим выбирается на экране обработки.
Для асинхронного режима задаётся лимит от 1 до 30 одновременно обрабатываемых документов
этого пайплайна; остальные задачи сохраняют статус `queued` до освобождения слота.
API сохраняет исходник в S3,
затем одной транзакцией создаёт задачу и событие отправки в PostgreSQL (transactional outbox).
Отдельный диспетчер публикует в Redis UUID задачи, поколение запуска, UUID события и приоритет Celery.
Если Redis недоступен или диспетчер перезапущен, событие остаётся в базе и отправка повторяется.
Воркер читает файл из S3, выполняет OCR и извлечение, затем одной короткой транзакцией
сохраняет документ и завершает задачу. Статусы: `queued`, `processing`, `succeeded`, `failed`.
Успешные документы доступны в истории; неудачные задачи сохраняют исходник для повтора.

Для интеграции добавьте `?background=true` к существующему пути запуска:

```bash
curl -H "Authorization: Bearer ocr_..." -F "file=@scan.pdf" \
  'http://127.0.0.1:5173/api/v1/pipelines/invoices_2026/run?background=true'
```

Ответ HTTP 202 содержит `taskId`, `status` и `statusUrl`.
Запрашивайте `GET /api/v1/jobs/{taskId}` с тем же ключом. При `succeeded`
ответ содержит `documentId`, `text` и `result`; при `failed` — `error` и `failedStage`.
Поле `stage` доступно во всех состояниях и принимает значения `queued`, `downloading`,
`recognition`, `extraction`, `validation`, `saving`, `completed` или `failed`.
При автоматическом повторе задача снова получает `stage=queued`, а `failedStage` сохраняет
этап предыдущего сбоя. После успешного завершения `failedStage` удаляется.
Ключ видит только задачи своего клиента в разрешённых пайплайнах, администратор — все. Отозванный ключ теряет доступ.
`background=true` явно выбирает асинхронный режим, `background=false` — синхронный.
Если параметр не передан, API выбирает синхронный режим, когда он разрешён, иначе
асинхронный. Запрос запрещённого для пайплайна режима возвращает HTTP 400.

При недоступности Redis API возвращает HTTP 202 после сохранения задачи: публикацией
и её повторами занимается диспетчер. Ошибка загрузки в S3 или записи в PostgreSQL возвращает HTTP 503.
Для ручного повтора вызовите `POST /api/v1/jobs/{taskId}/retry`. Повтор допустим для `queued` и `failed`,
использует тот же исходник и UUID, создаёт новое поколение запуска и сбрасывает лимиты попыток;
ключу должен быть по-прежнему разрешён этот пайплайн.
Пути `/api/jobs/{taskId}` и `/retry` также доступны.
При таймауте ожидания интерфейс сохраняет UUID и повторно проверяет ту же задачу.
UUID на странице не сохраняется после перезагрузки; готовые результаты остаются в истории.

Воркер кратко блокирует строку, чтобы получить аренду задачи с уникальным токеном.
Во время S3, OCR и вызовов модели транзакция PostgreSQL закрыта.
Диспетчер восстанавливает задачи с истёкшей арендой; старое поколение сообщения
и устаревший токен не могут записать результат. Документ сохраняется с фиксированным UUID.
Вызовы внешней модели могут повториться, если воркер погиб до фиксации результата.
Используются позднее подтверждение сообщения и `worker_prefetch_multiplier=1`;
см. [документацию Celery](https://docs.celeryq.dev/en/stable/userguide/tasks.html).

У пайплайна задаётся приоритет фоновой обработки от `0` до `9`. В Redis значения
обратные: `0` — высокий, `5` — обычный по умолчанию, `9` — низкий. Приоритет сохраняется в задаче и outbox,
передаётся Celery при первой отправке и при повторе. Redis настроен на десять уровней
приоритета; высокий приоритет влияет на порядок ожидающих сообщений, но не прерывает
задачу, которую воркер уже начал выполнять. Синхронная обработка приоритет не использует.
Лимит параллельности пайплайна проверяется атомарно перед переходом задачи в `processing`;
он общий для всех клиентов, запускающих этот пайплайн.

Временные сетевые ошибки, HTTP 429/5xx OCR и LiteLLM и временные ошибки S3
повторяются автоматически с задержками 10 и 20 секунд; постоянные ошибки, включая
неверный Structured Output, завершают задачу сразу. `attempts` доступно в ответе статуса.
По умолчанию разрешено 3 попытки и 600 секунд с первого захвата задачи, включая задержки повторов.
Одна попытка имеет soft limit 240 секунд, hard limit 270 секунд и аренду 300 секунд.
Настройки: `OCR_JOB_TIMEOUT_SECONDS`, `OCR_JOB_MAX_ATTEMPTS`, `OCR_JOB_RETRY_DELAY_SECONDS`,
`OCR_TASK_SOFT_LIMIT_SECONDS`, `OCR_TASK_HARD_LIMIT_SECONDS`, `OCR_JOB_LEASE_SECONDS`,
`OCR_CLIENT_ACTIVE_JOB_LIMIT` (по умолчанию `10`). Последний параметр ограничивает сумму
фоновых задач `queued + processing` одного клиента; все его API-ключи используют общий лимит.
Одиннадцатая задача получает HTTP 429 и `Retry-After: 5`. Завершённые и неудачные задачи
слоты не занимают; ручной повтор требует свободного слота. Синхронная обработка в лимит Celery не входит.
Синхронная обработка имеет отдельные распределённые лимиты: `OCR_GLOBAL_SYNC_LIMIT=10`
на всю систему и `OCR_CLIENT_SYNC_LIMIT=4` на одного клиента. Все ключи клиента используют
общий лимит. При заполнении API сразу возвращает HTTP 429 и `Retry-After: 5`; запрос не ждёт
освобождения слота. Слот удаляется после ответа, а после аварии API истекает автоматически.
Должно соблюдаться `soft < hard < lease`. Синхронный запуск ограничивает время OCR/извлечения
общим таймаутом и возвращает HTTP 504 при его превышении.

Логи Docker: `docker compose -f docker_compose.yaml logs -f worker dispatcher migrate`.
Один Linux worker по умолчанию выполняет четыре задачи (`OCR_WORKER_CONCURRENCY=4`).
Для роста общей параллельности запустите несколько worker-контейнеров, например
`docker compose -f docker_compose.yaml up -d --scale worker=3` даст до 12 одновременно
выполняющихся Celery-задач. Фактический предел дополнительно ограничивается настройками пайплайнов.
Для отдельных процессов задайте `OCR_EXTERNAL_WORKER=1` и запустите `npm run worker`
и `npm run dispatcher` в отдельных терминалах. На Linux используется стандартный пул процессов, на Windows —
`solo` для локальной разработки; для развёртывания используйте Linux-контейнер Docker.
Жёсткие лимиты Celery требуют пула процессов Linux. Воркеру нужны те же настройки
PostgreSQL, S3, LiteLLM и прокси, что API; диспетчеру — PostgreSQL, Redis и лимиты задач.

## LiteLLM

Скопируйте `.env.example` в `.env`, задайте `LITELLM_BASE_URL` и при необходимости `LITELLM_API_KEY`. Адрес может быть с `/v1` или без него. Ключ использует только Python-сервер.

Если в старом `.env` осталась строка `DATABASE_URL=sqlite:///...`, замените её адресом PostgreSQL или удалите для использования `POSTGRES_*`. Старые `OBJECT_STORAGE_*` больше не используются.

Для корпоративного прокси задайте `PROXY_URL` в `.env` — один адрес на все исходящие запросы: внешний OCR-сервис, LiteLLM и установку Python-зависимостей. Например `PROXY_URL=http://user:password@proxy.company.local:8080`. Адрес без протокола автоматически дополняется `http://`, поддерживаются схемы `http`, `https`, `socks5`; значение с другой схемой игнорируется с предупреждением в логе. Исключения перечисляйте в `NO_PROXY` (например `localhost,127.0.0.1`).

`PROXY_URL` перекрывает `HTTP_PROXY` и `HTTPS_PROXY`; если он не задан, эти переменные по-прежнему работают. Какой прокси применён, видно в тексте ошибки 502 и в предупреждении в логе сервера. Адреса показываются без логина, пароля, query-параметров и fragment; секреты из настроек скрываются в логах приложения. Ошибки сертификатов исправляйте настройкой доверенного корпоративного CA (например, `SSL_CERT_FILE`); проверка TLS остаётся включённой.

## Доступ и API-ключи

Внизу бокового меню находится карточка текущего пользователя: имя, роль, настройки
(пока без действий) и выход. Администратору также доступен раздел «Пользователи».
В нём можно создать приглашение, изменить роль коллеги и удалить учётную запись.
Приглашение — одноразовая ссылка на создание пароля со сроком действия 72 часа;
ссылку нужно скопировать и передать пользователю самостоятельно, email не отправляется.

Учётные записи имеют роли `admin` и `user`. Администратор управляет пользователями,
пайплайнами и API-ключами. Обычный пользователь запускает сохранённые пайплайны,
просматривает общую историю рабочего пространства и правит поля документов.
Изменение роли учитывается при следующем API-запросе. Удаление отзывает сессии
и приглашения, сохраняя историю документов. Нельзя удалить себя или изменить свою
роль; основной администратор из `.env` также защищён от удаления и смены роли.
Пароли приглашённых пользователей хранятся как scrypt-хэши с индивидуальной солью.
Миграция `0004_users` добавляет таблицу пользователей и связывает с ней сессии;
старые сессии основного администратора продолжают работать.

При создании пайплайна сервер автоматически генерирует **ID в формате UUID v4**.
В `POST /api/pipelines` передаётся конфигурация без `id`; созданный ID возвращается в `pipeline.id`.
Этот ID используется в API: `/api/v1/pipelines/{id}/run`.
После сохранения ID доступен только для чтения. Существующие пайплайны и импорт
старых конфигураций сохраняют свои ID; изменить ID через `PATCH` нельзя.

Интерфейс и API закрыты. В интерфейс входят по логину и паролю администратора: задайте `OCR_ADMIN_LOGIN` и `OCR_ADMIN_PASSWORD` в `.env` (пароль не короче 8 символов). Без `OCR_ADMIN_LOGIN` логин — `admin`. Без `OCR_ADMIN_PASSWORD` сервер при первом запуске генерирует пароль и сохраняет его в `data/admin-password.txt`; путь пишется в лог. После входа браузер получает сессию на 12 часов (cookie `HttpOnly`, `SameSite=Strict`); при работе по HTTPS добавьте `OCR_SECURE_COOKIE=1`. Смена логина или пароля завершает все открытые сессии.

Пароль хранится только в `.env` или в файле, в базе — лишь его медленный хэш (scrypt) для привязки сессий. После 10 неудачных попыток за 10 минут вход блокируется до конца этого окна. Счётчик хранится в PostgreSQL, общий для всех клиентов и экземпляров API и сохраняется после перезапуска: пока идёт перебор, войти не сможет и настоящий администратор.

Для внешних систем сначала создаётся клиент и выбираются доступные ему пайплайны, затем для клиента выпускаются API-ключи. Документы и фоновые задачи принадлежат клиенту, поэтому ключ можно безопасно заменить: новый ключ того же клиента увидит его историю, а ключ другого клиента — нет. Сам ключ показывается один раз — в базе хранится только его SHA-256-хэш. У ключа отдельно включаются права на запуск, чтение результата по ID и чтение списка истории. Владелец выпущенного ключа не меняется; для другого клиента создаётся новый ключ.

Снятие пайплайна у клиента сразу закрывает через API запуск, историю, результаты и задачи этого пайплайна, включая созданные ранее. Документы сохраняются и остаются доступны администратору; после возврата пайплайна клиент снова получает доступ. Удалённый пайплайн также закрывает старые результаты. Ключ передаётся в заголовке `Authorization: Bearer ...` и в зависимости от прав разрешает:

- `GET /api/v1/pipelines` — назначенные ключу пайплайны;
- `POST /api/v1/pipelines/{id}/run` — обработка документа из поля формы `file`;
- `POST /api/v1/pipeline/run` с полями `file` и `pipeline_id` — то же самое;
- `GET /api/v1/documents?page=0` — доступная ключу история документов клиента по 50 записей (`hasMore` — есть ли следующая); требуется право `history`;
- `GET /api/v1/documents/{id}` — документ клиента: распознанный текст, результат и извлечённые поля, включая правки оператора; требуется право `results`;
- `GET /api/v1/jobs/{id}` — статус и результат фоновой задачи клиента; требуется право `results`;
- запуск и повтор фоновой задачи требуют права `run`. Если у ключа есть `run`, но нет `results`, синхронный запуск возвращает только имя файла, `documentId` и статус без текста и результата.

Ключ видит только документы, которые обработал сам. Документы других ключей, загруженные через интерфейс и обработанные до появления этой возможности, для него не существуют — сервер отвечает 404. Если ключ отозвать и выпустить новый, документы старого ключа новому недоступны, а в истории у администратора они остаются. Исходный файл и правка полей ключу недоступны.

`/v1` — API интеграций. Изменение контракта: список пайплайнов теперь содержит публичную схему вместо конфигурации, а структурированный `result` возвращается объектом вместо JSON-строки. Обновите клиентов, вызывавших `JSON.parse(result)`. Адреса без версии (`/api/pipelines`, `/api/pipelines/{id}/run`, `/api/pipeline/run`) тоже остаются рабочими: ими пользуется интерфейс и уже подключённые системы. Служебные разделы — ключи, вход, исходные файлы и правка документов — под `/api/v1` не публикуются.

Swagger на `/api/docs` (и схема `/api/openapi.json`) описывает только эти семь маршрутов
`/api/v1` — контракт выгрузки во внешние учётные системы. Маршруты интерфейса
(вход, пользователи, ключи, клиенты, LiteLLM, история и правка документов, версии без
`/v1`, `/api/health`) помечены `include_in_schema=False`: они работают как прежде, но в
документации не показываются, чтобы интегратор видел ровно свой контракт. Состав схемы
закреплён тестом `test_schema_documents_only_the_integration_api` — новый маршрут не
попадёт в публичную документацию молча.

Передать свою конфигурацию пайплайна, открыть общую историю документов, настройки или другие ключи с ключом интеграции нельзя — сервер отвечает 403. Отозванный ключ получает 401. Пароль администратора в заголовке `Authorization` не принимается — только ключи интеграций.

```bash
curl -H "Authorization: Bearer ocr_..." -F "file=@scan.pdf" http://127.0.0.1:5173/api/v1/pipelines/pl_.../run
```

## Тестовый сервис интеграции

Запустите основное приложение (`npm run dev`), а во втором терминале — отдельный сервис:

```powershell
npm run simulator
```

Откройте http://127.0.0.1:5180. Создайте ключ в разделе «API-ключи» основного приложения,
назначьте ему пайплайн и вставьте ключ в тестовую страницу. Нажмите «Подключиться»,
выберите пайплайн и файл, затем «Отправить на обработку». Это реальная обработка:
файл сохранится в OCR, модели вызываются согласно настройкам пайплайна.

«Импортировать / обновить» получает все страницы документов этого ключа и полные
результаты с актуальными полями. Измените поля в истории OCR и повторите импорт,
чтобы увидеть обновление без дублей. Документы, загруженные через основной интерфейс
или другим ключом, здесь не отображаются. При ошибке импорта предыдущая локальная
копия сохраняется. При параллельной загрузке новых документов повторите импорт после
завершения обработки: API использует постраничную выборку без фиксированного снимка.

На странице есть просмотр JSON, скачивание импортированных данных и журнал HTTP-запросов
без ключа. Ключ и локальные результаты не сохраняются после перезагрузки страницы.
Смена ключа очищает результаты. При таймауте отправки проверьте импорт/историю перед
повтором: сервер мог завершить обработку, повторная отправка создаст новый документ.

Сервис слушает только `127.0.0.1`. По умолчанию он обращается к Python API на порту
`BACKEND_PORT` (8000). В `.env` можно задать `SIMULATOR_API_URL` (например,
`http://127.0.0.1:5173`, адрес сервера без `/api/v1`) и `SIMULATOR_PORT` (по умолчанию 5180).
Дополнительные зависимости не нужны. Проверка: `npm run test:simulator`.

## Хранение данных

JSON-колонки PostgreSQL используют `JSONB`: поля документов, конфигурации пайплайнов
и задач, клиентов интеграций, разрешения API-ключей и счётчик входа. Миграция `0008_integration_clients`
создаёт отдельного клиента для каждого существующего ключа и переносит к нему документы и задачи этого ключа.
Миграция `0003_jsonb` преобразует
существующие колонки при обновлении схемы; значения сохраняются.

- PostgreSQL — история, пайплайны, API-ключи, сессии, распознанный текст, первоначальный ответ модели и отредактированные поля.
- S3 — новые исходные файлы под внутренними UUID, ключи объектов хранятся в базе.
- `data/originals/` — старые локальные исходники, если они были сохранены до перехода на S3.
- `data/admin-password.txt` — сгенерированный пароль администратора, если `OCR_ADMIN_PASSWORD` не задан.
- Пайплайны доступны через API; при открытии списка ранее сохранённые конфигурации из браузера автоматически импортируются на сервер.

Схемой управляет Alembic: миграции лежат в `backend/db/migration/versions`, версия —
в таблице `alembic_version`. API применяет миграции при старте, Docker делает это также
отдельным сервисом до запуска остальных процессов. Для отдельного обновления выполните
`npm run migrate`. Миграции PostgreSQL сериализуются advisory lock, поэтому параллельные
старты API не изменяют схему одновременно. Первая миграция принимает существующие таблицы
без удаления данных и добавляет отсутствующие старые столбцы документов; следующая
добавляет аренды, попытки, outbox и ограничитель входа. Ранее созданные незавершённые
задачи подхватывает диспетчер. Автоматического переноса SQLite в PostgreSQL нет.
Перед обновлением рабочей базы сделайте резервную копию. Откат первой миграции запрещён,
поскольку её таблицы могли существовать до Alembic.

Старая D1-база, SQLite и R2-файлы автоматически не переносятся и не удаляются. Для резервной копии остановите приложение, сделайте дамп PostgreSQL через `pg_dump`, скопируйте всю папку `data` и сохраните соответствующие объекты S3. Путь локальной папки можно изменить через `OCR_DATA_DIR`. Данные общие для пользователей одного экземпляра приложения.

## TaskService

`backend.service.tasks.TaskService` хранит задачи
и ссылки на их файлы. Миграция `0006_tasks` создаёт таблицы и тип документа `generic`.
Тип передаётся в поле `document_type` DTO (по умолчанию `generic`); другие типы должны
быть предварительно добавлены в `document_types`.
Поле `content_type` — это MIME-тип файла по `document_link` (в ссылке расширения может
не быть); оно обязательное, не проверяется на формат и сохраняется в `task_files`
(миграция `0013_task_content_type`, колонка nullable ради ранее созданных строк).
Набор полей DTO повторяет контракт внешней системы постановки задач.
Сервис предоставляет `create_task`, `update_task_status`, `get_status_by_code`,
`is_task_existing` и `get_task_data`. Это слой хранения: запуск OCR и отправка callback
в него пока не подключены.

```python
from backend.db.domain.models import TaskStatus
from backend.schema.api import InitTaskRequestDTO
from backend.service.tasks import TaskService

with sessions() as db:
    TaskService.create_task(InitTaskRequestDTO(
        task_code="task-123",
        callback_url="https://integration.example/callback",
        document_link="s3://documents/input.pdf",
        content_type="application/pdf",
    ), db)
    TaskService.update_task_status("task-123", TaskStatus.PROCESSING, db)
```

Методы записи фиксируют переданную сессию; используйте отдельную сессию для операции.
При ошибке выполняется rollback и исключение передаётся вызывающему коду.
`False` при обновлении и `None` при чтении означают отсутствие задачи.
Повторный `task_code` вызывает `IntegrityError`. Статусы принимаются как enum или строка
без учёта регистра; числовые коды: `0=PENDING`, `1=PROCESSING`, `2=DONE`, `3=ERROR`,
`4=RESPONSE_SENDING_ERROR`. Время записывается в UTC. Повторное финальное обновление
сохраняет время завершения; перевод в рабочий статус очищает его.

## Обработка и история

Конструктор состоит из трёх этапов: название, источник и обработка. На этапе
обработки промпт и поля извлечения включаются независимо. Только промпт возвращает
свободный текст; только поля — JSON; при включении обоих промпт задаёт дополнительные
правила извлечения полей в одном запросе к модели. При отключении обоих результатом
остаётся исходный текст. Настройки отключённых блоков сохраняются для повторного включения.
Для сканов на том же этапе настраивается OCR; его можно отключить, если у файла есть
текстовый слой. Изображения и PDF без текстового слоя требуют включённого OCR.
В API переключатели сохраняются как `extraction.prompt_enabled`,
`extraction.fields_enabled` и `ocr.enabled`. Старые конфигурации с `mode=prompt`
или `mode=fields` продолжают работать без этих переключателей.

В режиме «Отдельные параметры» извлечение использует Structured Output:
`response_format.type=json_schema`, `json_schema.strict=true`, все указанные поля
в `required`, `additionalProperties=false`. Типы полей: `string`, `number`, `integer`, `boolean`, `object`, `array` (список объектов).
У объектов и элементов списков задаются вложенные поля, до 6 уровней. Все поля обязательны;
если значение не найдено, возвращается `null`, для явно пустого списка — `[]`.
Старые поля без типа считаются строками. Внутренние инструкции (`description`) передаются только модели;
публичные описания (`public_description`) попадают в схему API.
API дополнительно проверяет JSON, точный состав полей и типы значений.
Неверный ответ, отказ модели или незавершённая генерация возвращают HTTP 502
при синхронном запуске либо статус `failed` через Celery; документ в историю не добавляется.
Пустой список полей и повторяющиеся имена не допускаются.

Выбранная модель и настройки LiteLLM должны поддерживать `json_schema`.
Автоматического перехода в JSON mode при ошибке нет.
См. [Structured Output в LiteLLM](https://docs.litellm.ai/docs/completion/json_mode).
Режим «Целый промпт» возвращает свободный текст.

`POST /api/pipeline/run` принимает файл (до 20 МБ) и конфигурацию пайплайна. Текстовые файлы читаются в UTF-8, PDF с текстовым слоем — через pypdf, DOCX — через python-docx. Сканы отправляются в выбранную vision-модель LiteLLM или в OCR-сервис, адрес которого указывается в мастере. Вместе с файлом уходят поля формы из `ocr.options` пайплайна, если они там заданы (например `model_name` и `force_ocr`). Текст берётся из `page_content`, `text` или `result` ответа. Для внутреннего сервиса при заданном `PROXY_URL` добавьте его хост в `NO_PROXY`. Опциональный шаг извлечения возвращает JSON.

Успешно обработанный документ появляется в `/history`. Можно открыть исходник (PDF и изображения), скачать файл, прочитать распознанный текст и изменить поля. Изменения не затрагивают оригинал и исходный ответ модели. Конфликтующие правки из другой вкладки возвращают HTTP 409.

## Архитектура и команды

Бэкенд разложен по слоям: слой выше знает о слое ниже, обратных зависимостей нет.
Бизнес-логика не импортирует FastAPI — она возбуждает ошибки из `backend/core/errors.py`,
а в HTTP-ответ их превращает единственный обработчик в `backend/server.py`.

- `backend/server.py` — сборка FastAPI, маршрутизация и обработчики ошибок.
- `backend/core/` — конфигурация и прокси (`config.py`), скрытие секретов и логи (`security.py`), доменные ошибки (`errors.py`), учётные данные администратора (`secrets.py`), жизненный цикл приложения (`lifespan.py`).
- `backend/api/v1/` — API интеграций с общим префиксом `/api/v1`: пайплайны, документы, задачи и обработка.
- `backend/api/` — административные маршруты, вход (`auth.py`), ключи и клиенты (`keys.py`), политики доступа (`policies.py`); адреса без версии используют общие обработчики v1 с сохранением прежних прав доступа.
- `backend/schema/` — конфигурация пайплайна (`pipeline.py`), контракты HTTP (`api.py`, `access.py`).
- `backend/service/` — обработка документа (`processing.py`), распознавание и извлечение (`recognition.py`), проверка ответа модели (`validation.py`), задачи, учётные записи и ограничитель входа.
- `backend/handler/` — внешний мир: LiteLLM (`litellm.py`), OCR-сервис (`ocr_service.py`), чтение файлов (`documents.py`), S3 (`storage.py`), Keycloak.
- `backend/db/` — таблицы (`domain/models.py`), соединения и репозитории (`infra/`), миграции Alembic (`migrate.py`, `migration/`).
- `backend/worker/` — Celery (`celery_app.py`), воркер (`tasks.py`) и диспетчер доставки/восстановления (`dispatcher.py`).
- `app/api/[...path]/route.ts` — передача запросов из интерфейса в Python без CORS.
- `scripts/run-app.mjs` — подготовка Python и управление локальными процессами.

```powershell
npm run backend:setup # только подготовка Python
npm run test:backend  # API-тесты на временной базе, без реальных вызовов LiteLLM
npm run worker        # отдельный Celery worker
npm run dispatcher    # отдельный диспетчер outbox и восстановления задач
npm run migrate       # применить миграции до текущей версии
npm run build         # сборка интерфейса
npm start             # API + воркер + диспетчер + собранный интерфейс
```

Python API слушает `127.0.0.1:8000`, интерфейс — `127.0.0.1:5173`. Порты можно изменить через `BACKEND_PORT` и `PORT`. `BACKEND_URL` позволяет направить интерфейс к отдельно размещённому API. Для отдельного запуска Python: `.venv\Scripts\python.exe -m uvicorn backend.server:app --host 127.0.0.1 --port 8000` (Linux/macOS: `.venv/bin/python`).

Развёртывание требует Docker либо сервера с Node.js и Python, PostgreSQL и доступа к S3. Сохраняйте Docker volume PostgreSQL и папку `data` между запусками. Старый сценарий публикации в Cloudflare Workers/Sites больше не используется. Для доступа извне поставьте reverse proxy с HTTPS перед портом интерфейса и задайте `OCR_SECURE_COOKIE=1`; порт Python API наружу не открывайте.


## Список пайплайнов для интеграции

`GET /api/pipelines` возвращает `{"pipelines": [...]}`. Каждый элемент содержит
`id`, `name`, `source`, `ocr`, `extraction`, `createdAt` и `updatedAt`.
В `ocr` и `extraction` сохраняются настройки моделей, температуры, промпты и поля.
Пустой список возвращается как `{"pipelines": []}`.

Интеграция получает назначенный список через `GET /api/v1/pipelines` и запускает
сохранённый пайплайн по ID: `POST /api/v1/pipelines/{id}/run` с полем формы `file`.
Передача произвольной конфигурации в поле `pipeline` доступна только администратору
через `POST /api/pipeline/run`.

Конструктор сохраняет конфигурации через `POST /api/pipelines` и
`PATCH /api/pipelines/{id}`; удаление — `DELETE /api/pipelines/{id}`.
Старые пайплайны импортируются при первом открытии списка в исходном браузере;
до этого сервер не может прочитать данные этого браузера. Импорт не перезаписывает
существующие серверные конфигурации и не восстанавливает удалённые.


## Существующий Keycloak

Новый сервер Keycloak и его образ не нужны. Интеграция подключается к существующему
сервису. Пока параметры не заполнены, используется прежний локальный вход.
Чтобы переключиться, задайте в `.env`:

```dotenv
AUTH_PROVIDER=keycloak
APP_PUBLIC_URL=https://ocr.example.com
KEYCLOAK_URL=https://identity.example.com
KEYCLOAK_REALM=company
KEYCLOAK_CLIENT_ID=ocr
KEYCLOAK_CLIENT_SECRET=<секрет конфиденциального клиента>
KEYCLOAK_SESSION_KEY=<ключ Fernet>
```

`KEYCLOAK_URL` — адрес сервера без `/realms/...`; для старых установок сохраните
префикс `/auth`, если он есть. `APP_PUBLIC_URL` — внешний адрес интерфейса без пути,
доступный браузеру. HTTPS обязателен, кроме localhost для разработки.
Ключ шифрования создаётся один раз:

```powershell
.venv\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Храните ключ вне Git и одинаковым на всех экземплярах API. Смена ключа завершит
существующие сессии. Реальные секреты не добавлены в репозиторий.

В Keycloak настройте OIDC-клиент: Client authentication включено, Standard flow
включён, PKCE S256, подпись токенов RS256. Direct access grants приложению не нужны.
Valid redirect URIs: `https://ocr.example.com/api/auth/keycloak/callback`;
Valid post logout redirect URIs: `https://ocr.example.com/login`.
Замените домен на `APP_PUBLIC_URL`. Не используйте wildcard для redirect URI.

Создайте отдельные роли клиента `admin` и `user`, назначьте хотя бы одного
администратора. Роли должны попадать в access token в
`resource_access.<KEYCLOAK_CLIENT_ID>.roles`; для стандартного маппера подключите
client scope `roles`. Имена меняются через `KEYCLOAK_ADMIN_ROLE` и
`KEYCLOAK_USER_ROLE`. Для существующих realm-ролей есть `KEYCLOAK_ROLE_SCOPE=realm`;
предпочтительнее роли клиента, чтобы не предоставлять доступ из-за роли другого приложения.
Без роли приложения вход запрещён. Настройки role scope проверяйте по выпущенному
токену в Keycloak, без публикации токена.

Для списка пользователей, приглашений и изменения ролей дополнительно задайте
`KEYCLOAK_ADMIN_CLIENT_ID` и `KEYCLOAK_ADMIN_CLIENT_SECRET` отдельного клиента
с Client authentication и Service accounts. Выдайте его service account права
просмотра пользователей и клиента приложения, изменения пользователей и назначения
только двух ролей OCR. При использовании стандартных realm-management ролей
нужны `query-users`, `view-users`, `manage-users`, `view-clients`; предпочтительнее
ограничить полномочия через fine-grained admin permissions вашей версии Keycloak.
Настройте SMTP в realm: письма отправляет Keycloak через execute-actions-email,
срок ссылки — 72 часа. Для новой учётной записи письмо предлагает задать пароль
и подтвердить email; для существующей — подтвердить email без сброса её пароля.
Если отправка не удалась, назначенная роль отзывается; приглашение можно повторить.
Без сервисного клиента вход работает, но управление пользователями недоступно.

Список показывает только пользователей с ролями OCR, включая наследуемые роли.
Доступ через группы и составные роли редактируется в Keycloak; интерфейс защищает
таких пользователей от изменений. Для управления нужны несоставные роли OCR.
Удаление в интерфейсе отзывает роли приложения и его локальные сессии,
сохраняя общую учётную запись Keycloak и историю документов. Собственную роль
нельзя изменить, себя нельзя удалить. Другие роли и приложения не затрагиваются.
Для realm более 10 000 пользователей используйте администрирование в Keycloak:
список приложения ограничен, чтобы не отдавать неполные результаты.

В режиме Keycloak локальный пароль и локальные приглашения не работают;
неполная конфигурация останавливает запуск без перехода на локальную авторизацию.
API-ключи интеграций сохраняют прежний доступ. OAuth-токены остаются на сервере
в зашифрованном виде в PostgreSQL, браузер получает только HttpOnly cookie.
Вход использует Authorization Code + PKCE, одноразовый state и nonce,
проверку подписи по JWKS, issuer и клиента. Каждый защищённый запрос проверяет
активность токена в Keycloak; недоступный сервер даёт 503. Изменения ролей в самом
Keycloak подхватываются при обновлении токена (не позднее следующего запроса
после 60 секунд). Изменения через OCR сразу отзывают локальные сессии пользователя.
Выход очищает сессию OCR и перенаправляет браузер на завершение SSO в Keycloak.

Docker Compose уже передаёт `.env`, поэтому дублировать эти параметры в YAML
или добавлять сервис Keycloak не требуется. После настройки пересоберите образ
и перезапустите приложение. Подключение к вашему серверу нельзя проверить,
пока его адрес и параметры клиента не заданы.

Документация: [OIDC в Keycloak](https://www.keycloak.org/securing-apps/oidc-layers),
[Admin REST API](https://www.keycloak.org/docs-api/latest/rest-api/index.html).


### Публичная схема результата

`GET /api/v1/pipelines` возвращает `id`, `name`, публичное `description`, разрешённые
`executionModes`, `asyncConcurrency` для асинхронного режима и `resultSchema`.
API-ключ видит только назначенные ему пайплайны. Старый `GET /api/pipelines` с API-ключом
тоже скрывает конфигурацию; с пользовательской сессией он сохраняет полную конфигурацию для редактора.
Промпты, модели, URL OCR, параметры обработки и внутренние инструкции полей не публикуются.
Публичные описания заполняются отдельно: старые инструкции автоматически не копируются.

Пример одного элемента `pipelines`:

```json
{
  "id": "objects",
  "name": "Информация об объектах",
  "description": "Извлекает список объектов из документа",
  "resultSchema": {
    "type": "object",
    "properties": {
      "objects": {
        "type": ["array", "null"],
        "description": "Объекты документа",
        "items": {
          "type": "object",
          "properties": {
            "name": {"type": ["string", "null"], "description": "Название объекта"},
            "area": {"type": ["number", "null"], "description": "Площадь"}
          },
          "required": ["name", "area"],
          "additionalProperties": false
        }
      }
    },
    "required": ["objects"],
    "additionalProperties": false
  }
}
```

Схема описывает поле `result`, а не весь ответ. `/api/v1` возвращает структурированный результат
как JSON-объект при синхронной обработке, в статусе фоновой задачи и в деталях документа.
Без извлечения полей схема равна `{"type":"string"}`, даже если текст похож на JSON.
Маршруты обработки без `/v1` сохраняют прежний строковый формат `result`.
Снимок публичной схемы хранится с новым документом (миграция `0007_result_schema`);
изменение настроек пайплайна не меняет формат уже полученного результата.
Поле `fields` истории по-прежнему содержит отдельные правки оператора, `result` — исходный ответ модели.
